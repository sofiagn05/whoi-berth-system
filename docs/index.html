An Automated Reservation and Verification System for WHOI's Berths

WHOI's dock schedule has been maintained as a spreadsheet grid, reviewed manually for two operational risks: berths double-booked for overlapping dates, and vessels assigned to slips they do not physically fit. This system replaces that manual review with automated checks, designed and validated against the facility's full 23-year booking history.

Starting Conditions

A spreadsheet workbook, reviewed manually

  • A 23-tab workbook (1997–2019): berths as rows, days as columns, occupant names entered as free text
  • Berth length embedded in row labels; no structured fields anywhere in the source
  • No vessel dimension data (length, beam, draft) recorded in the schedule
  • Double-bookings identified only through manual visual review of the grid
  • No mechanism to confirm a vessel physically fits its assigned berth
  • Formatting inconsistent across years: three distinct header layouts, unlabeled rows, one mislabeled year
Approach

Design the system, then validate it against the full record

  • A structured application (FastAPI, SQLite) with a normalized data model for berths, vessels, and bookings
  • Automatic double-booking rejection, applied at entry and re-verified retroactively across all 23 years
  • Automatic fit-checking against length, beam, and draft, with unknown data treated as its own explicit state
  • An import pipeline engineered to handle every year of source data, not only an initial sample
  • A utilization dashboard, a conflict-resolution engine, full-history search, and bulk data import
  • 21 automated tests, continuous integration on every change, and a written specification of requirements and verification

1. Core Requirements

Double-Booking Detection

Every new reservation is checked against existing reservations on the same berth for overlapping dates. A conflicting request is rejected and identifies the specific reservation it collides with; the full history can also be re-audited on demand.

Physical Fit Verification

A vessel exceeding a berth's length is rejected outright; a berth offering less than the standard 10% clearance margin generates a warning. Beam and draft are checked the same way. When a dimension is unknown, the system states that explicitly rather than assuming a pass.

2. Capabilities Beyond the Core Requirements

Berth Recommendation

Ranks available, fitting berths by efficient use of space, favoring channel-adjacent berths for deep-draft vessels and easier-access berths for guest or novice crews.

Utilization Dashboard

Reports berth occupancy, double-booked days by month, and highest-usage vessels — visibility an audit list alone does not provide.

Conflict Resolution Engine

Resolves every outstanding conflict in a single pass using a proven scheduling algorithm that mathematically guarantees the best possible outcome, rather than correcting bookings one at a time.

Full-History Search

Locates a vessel or event by name across all 23 years and navigates directly to the matching record, without paging through individual months.

Bulk Dimension Import

A CSV upload populates vessel length, beam, and draft by name. Verified in production use to reduce open fit-verification warnings from 31 to 1 on the initial data subset.

Interactive Schedule Grid

The same berth-by-day layout staff have relied on, rebuilt as a working interface: select to book, select to inspect, conflicts flagged automatically.

Documented Override Workflow

A booking that only trips a soft warning (marginal clearance, for example) can be approved deliberately rather than automatically blocked, and the system requires a stated reason, preserving a clear record of every exception.

RESTful API with Live Documentation

Every function — booking, search, dimension import, conflict resolution — is exposed through a documented API with interactive, auto-generated reference documentation, so the system can integrate with other tools, not only its own interface.

Automatic Vessel Classification

Vessel type is inferred directly from standard designation prefixes (research, fishing, motor, sailing, tug, barge) during import, populating the registry without manual data entry.

Repeatable, Non-Destructive Import

Re-running the import against updated source records never creates a duplicate booking; existing data is checked before anything new is written, so the process can be run again at any time with no cleanup required.

Tidal and Maneuverability-Aware Placement

Berths are categorized by physical characteristics — channel-adjacent, T-head, alongside, inner — and both the recommendation and resolution engines factor these into placement, not length alone.

Capability Spotlight

Priority-Aware Conflict Resolution

Not all of WHOI's work carries equal operational stakes. A funded, time-boxed expedition — supporting ocean-climate solutions, deep-sea engineering, or ecological resilience research under initiatives such as the Campaign for Our Ocean Planet — is not interchangeable with a routine guest visit when a berth conflict has to be resolved. This system makes that distinction explicit rather than treating every reservation as equally displaceable.

Every booking carries a priority tier. The conflict-resolution engine ranks priority ahead of reservation length: a two-day critical mission is protected over a twenty-one-day routine booking it conflicts with — the reverse of what a length-only rule would produce. This was confirmed both in isolated testing and against a live database, not assumed from the algorithm design alone.

3. Data Quality Findings Across 23 Years of Records

Each finding below was identified by running the import process against the complete, unmodified source workbook and auditing its output for correctness — not by inspecting the code in isolation.

Three header layouts, one parser
The month header, weekday row, and day-number row appear in three distinct arrangements across the workbook. The least common arrangement, where day numbers are embedded in the header itself, initially produced zero bookings for 15 of the 23 years.
Unlabeled berth rows
Rows containing real bookings but no berth name were indistinguishable from a blank row marking the end of a month, causing the reservation to be dropped. These are now retained under an explicit "Unidentified" berth category.
Non-standard berth names
Two berths — "North Finger Piers" and "Small craft slips (institution boats)" — do not follow the standard "Name - Length" format. Six years of Finger Piers bookings were excluded from import before this was identified and corrected.
Misread month boundaries
A month header written without its year was not recognized as the end of the prior month's block, causing that header row to be misread as a berth — producing invalid entries literally named "July" and "August."
A labeling error in the source
The 2010 tab's own November and December headers are mislabeled 2018, with vessel names positioned in what should be day-number cells. Accepting that row as valid produced incorrectly dated bookings and a fabricated vessel entry. A validation rule now requires day-numbering to begin at 1, rejecting the malformed row instead of guessing.
Operational notes recorded as vessels
Scheduling notes and maintenance entries (arrival times, "Bollard replacement, west face," "Fueling @0800") were being recorded as vessel bookings. These are now correctly classified as operational events, not reservations.

4. Engineering Process and Verification

Testing and Continuous Integration

Twenty-one automated tests were implemented, including a dedicated regression test for each finding above to prevent recurrence. A continuous integration pipeline runs the full suite on every change and identified a genuine configuration failure on its first execution.

A Dedicated Review Pass

Once the core functionality was complete, a separate review removed unused code, consolidated a function call duplicated across four locations into a single reference, and eliminated redundant logic — before any further features were added.

Reproducible Setup

A single command takes a clean environment to a fully running application loaded with all 23 years of data. This was confirmed by removing the local environment entirely and rebuilding it from nothing.

A Written Specification

A separate document records the problem statement, requirements with defined success criteria, real constraints, explicit assumptions, known limitations, and the method used to verify each component.
